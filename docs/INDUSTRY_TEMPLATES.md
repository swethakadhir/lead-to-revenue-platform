# Industry templates and tenant configuration

Phase 4 keeps one application and one schema for every industry. `industry_templates` contains four versioned starter configurations (`dental`, `salon`, `interior_design`, `custom`) as JSONB data. The source template supplies lead fields, appointment types, pipeline display names, qualification criteria, follow-up defaults, and terminology. No React or Server Action branches on industry key.

When an authenticated user creates a business, the server passes their verified user ID and the selected active template ID to the service-role-only `create_tenant_with_owner` RPC. PostgreSQL inserts the tenant and owner membership in one transaction. Tenant-insert triggers provision the generic 11 pipeline keys and copy the template into `tenant_settings`, `lead_field_definitions`, and `qualification_rules`. A failure rolls the transaction back. `tenants.currency` is canonical; `tenant_settings` has no currency field.

Tenant copies are independent of later global-template edits. The template ID records the source, not a live dependency. Existing tenants were additively backfilled with generic settings and fields, keeping `industry_template_id` null so an owner/admin can apply one named template later. Applying a template updates tenant configuration and stage *names*, without deleting existing stage keys, opportunities, or lead JSON. Old arbitrary `lead_data` keys remain readable and survive edits.

The same lead form component renders all active field definitions in `sort_order`. Values serialize to `leads.lead_data` JSONB; Server Actions fetch the active tenant's definitions and validate required fields, types, and allowed options. PostgreSQL additionally validates configured field types/options on direct writes while permitting historical unconfigured keys. Lead detail displays configured labels and gracefully labels unknown keys. The appointment form reads tenant appointment types; Server Actions and a database trigger reject newly selected unconfigured types while retaining unchanged legacy values.

Owners/admins may edit field labels, required/active state, order, and options, rename pipeline stage labels, and change appointment types at `/app/settings`. Sales, front-desk, and viewer roles can read configuration but not modify it. RLS is tenant-scoped; global templates are read-only to ordinary users. Configuration updates are recorded in `audit_logs`, readable only by tenant owners/admins. Qualification rules are deterministic criteria/configuration only; no AI scoring or automation is implemented in Phase 4.

To add a future industry, add a new `industry_templates` row in a versioned migration with the same JSONB keys and supported field types. The generic provisioner, lead renderer/validator, and appointment UI need no industry-specific changes. If a starter template needs a new version, add or update source data through a migration; existing tenants retain their copied settings until an explicit migration strategy is designed. This phase intentionally has no marketplace or automatic tenant-template upgrades.
